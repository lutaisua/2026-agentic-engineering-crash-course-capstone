# Store parent failure isolation checkpoint

Date: **2026-10-06**. Implementation follow-up to
[the Store development plan](../store-development-next-steps.md).
**v0.2 remains unaccepted; discovery task 2.9 remains incomplete.**

## Implementation and verification

The Store provider now catches child-query failures per parent and continues
other parents, retaining successful child results. Identical failure categories
are deduplicated. Unknown publication on successfully retrieved children remains
explicit alongside request failures. Authentication/credential-generation and
global request-budget failures stop further child queries; cancellation propagates.
Failed coverage never commits a complete snapshot or becomes a successful empty
collection. Publication classification is unchanged: absent/malformed evidence
remains unknown, not automatically draft-only.

Two regression tests cover a failed first parent followed by a successful child,
and repeated parent failures with an unknown-publication child. Three diagnostic
sanitizer tests cover private-payload exclusion, bounded error-body reads,
non-JSON errors, nested envelopes, case variants and constrained machine codes.
No response message, secret, token or actual product ID is logged by those probes.

The documented `scripts/verify.ps1` passed:

- Release build: **0 warnings, 0 errors**.
- **105 non-live tests**, no failures/skips.
- Formatting verification: passed.
- [Source manifest](v0.2-store-parent-isolation-source-hashes.json): **61 files**,
  all hashes matched after capture. Earlier manifests are retained.

The initial verifier was blocked by sandbox NuGet socket permissions; the
authorized rerun completed. A diagnostic-helper naming collision found during
build was corrected before the final passing verifier.

profile. Its normalized result was saved privately and only counts/categories

[per-app collection](https://learn.microsoft.com/en-us/windows/uwp/monetize/get-add-ons-for-an-app)

The latter was tested only as a diagnostic, not installed as a fallback provider.
The probe test completed, which means the diagnostic ran; it does not accept
the failing collection requests or prove complete account inventory.

Token/app requests succeeded. The prior identity-match diagnostic established
matching decoded audience/tenant/client values. The sanitized service error was
not a recognized machine code but contained a type-related signal. The operator
subsequently confirmed that all current publisher add-ons are **Subscription**.
This suggests a product-type contract issue but does not establish the backend
cause or prove subscriptions are unsupported. See the dated
[subscription investigation and support draft](store-subscription-inventory.md).
Microsoft's
[submission prerequisites](https://learn.microsoft.com/en-us/windows/uwp/monetize/create-and-manage-submissions-using-windows-store-services)
document unsupported features; do not convert this unclassified 400 into empty
or not-applicable coverage.

These calls use the existing protected credential resolver and bounded HTTP
boundary. Error inspection is limited to 16 KiB and exposes only constrained
machine codes and message-category booleans. No raw error body was saved.
No publishing, product creation/deletion or report-export request occurred.
